# v0.2.3 — the performance series

Everything between v0.2.2 and this tag is one sustained campaign: measure the
read and write paths honestly, then rebuild the hot loops column-major. Plus a
type-system upgrade for table creation, UTF-8 end to end, and a long tail of
correctness fixes the new tests caught.

## Performance

**Write path rebuilt — up to 6.6× (spec 057, 063, 064).** COPY/CTAS encode
column-major (one kernel call per column per chunk, never per value), fan out
across parallel bulk-load sessions (`mssql_copy_parallel_writers`, capped 8,
measured 10.55 s → 3.24 s at 4 writers on 44×1M), and pick TABLOCK from the
target's actual shape (`auto`: heap on, clustered off — the old rule
serialised clustered-columnstore loads). `mssql_copy_flush_rows` default moved
to 102 400 — SQL Server's own threshold for writing compressed columnstore
rowgroups directly (53 MB → 7 MB on the 1M-row measurement). Spec 064 made
the cursor path (any NULL or variable-width column — i.e. production) cost
what the strided path costs: decimal −42%, datetime −23%.

**Read path staged and batch-decoded — −14…−47% per family (spec 054, 055,
056, 058).** Rows stage column-major and decode in per-family batch kernels;
uniform chunks publish CONSTANT vectors (−14% DECIMAL / −15% NVARCHAR);
the row-completeness walk dispatches on per-column forms. Default TDS packet
size raised 4096 → 16 384 (`mssql_tds_packet_size`): −28% client CPU / −43%
wall on read, −27% CPU on write.

**UTF-8 on the wire (issue #225).** The extension advertises TDS UTF8SUPPORT;
servers that grant it send UTF-8-collated columns without UTF-16 transcoding:
85.8 MB → 43.9 MB and 0.44 s → 0.25 s for 1M ~41-char values.

## New

- **Declared string types (spec 060):** annotate columns as
  `x::MSSQL_VARCHAR(n [, 'collation'])` / `MSSQL_NVARCHAR(n)` in CTAS/COPY —
  lengths and collations land in the created DDL. Attached tables report these
  types back (`mssql_catalog_native_types`), so a target created from an MSSQL
  source inherits its lengths with no casts. Plus `string_length` and
  `table_kind` (HEAP / COLUMNSTORE) options and their global settings.
- **`mssql_reset_connection` (issue #189):** decide whether pooled connections
  reset session state (temp tables, SET options) between uses; honoured on
  every release path.
- **`MSSQL_COUNTERS=1`:** per-stream and per-COPY performance counters without
  the logging that used to distort them, including encode-path attribution.
- **TEXT / NTEXT / IMAGE columns are readable** (issue #197) — the legacy LOB
  wire forms have decoders now.
- **Partitioned tables work** (issue #85, spec 049): catalog metadata no
  longer duplicates per partition; the planner sees real row counts; the
  catalog reports each table's physical shape (heap / clustered /
  columnstore).

## Behavior changes

- **`mssql_utf8_collation` default is `Latin1_General_100_BIN2_UTF8`** (was a
  CI_AS collation): matches Microsoft Fabric's default and is accepted where
  the old default is not. BIN2 is case- and accent-SENSITIVE — override per
  column via `MSSQL_VARCHAR(n, 'collation')` or globally via the setting.
- **BIGINT (and other widening ints) may now target narrower integer columns**
  (issue #153): the encoder range-checks per row and refuses cleanly instead
  of demanding a schema change.
- **A source column of an incompatible type is accepted when it is entirely
  NULL** (`SELECT ..., NULL AS col`), and refused with a named pair the moment
  it carries a value — previously a bind error (or an INTERNAL error for
  unknown types, issue #238).
- `COPY ... TO` an existing table with unknown/unsupported source types now
  fails with a clear message instead of `INTERNAL Error` (#238); GEOMETRY
  columns land in `varbinary` as standard WKB.

## Fixed

- `SUM()` results (HUGEINT) can be COPY'd — BCP encodes HUGEINT as
  DECIMAL(38,0) with a range guard (issue #177).
- Four staged-read defects found by the new differential/fuzz suite (spec
  059): a `U+0000` inside a string mis-split the batch decode; `money`
  shifted negative values into UB; `datetime` day counts could overflow;
  a malformed `DATETIMEN` width over-read the heap.
- DATETIME day-count widening before epoch conversion (#222).
- Catalog-scan bind data serializes, so DuckDB's common-subplan optimizer can
  no longer feed one scan's rows to another (#211).
- Invalid UTF-16 from the server decodes to U+FFFD instead of failing the
  query; NBCROW/framing edge cases pinned by tests.
- The columnar NullOnly writer emitted a wrong NULL marker for
  USHORT-length/PLP columns (latent; exposed and fixed in spec 064).
- Integration suite actually runs in CI (issue #212): the old filter matched
  8 files and exited green; 172 files / ~5000 assertions run now.

## Compatibility

- DuckDB: built against v1.5.5-family main; `mssql_compat.hpp` covers the
  stable/nightly API split.
- SQL Server 2019/2022, Azure SQL, Microsoft Fabric; local
  version × charset compatibility matrix in `test/compat/` (#232).
