# Spec 080 — reconnaissance, 2026-10-08

Re-checks spec 080 (written 2026-09-17 on PR #364) against `main` at
`ed7cb2e` and the DuckDB pin `4fbae437b22`. Since the spec was written, these
have landed: 079 (the writer), 081 (`mssql_scan_unsafe`), 083 (RPC

The recon had four parts:

## 1. DuckDB at `4fbae437b22`

Paths are under `duckdb/src/`; "opt" means `optimizer/remote_pushdown_optimizer.cpp`.

- **Statements the rewriter handles** (opt:223-256): SELECT, INSERT, DELETE,
  UPDATE, MERGE INTO, CREATE, DROP, ALTER, and EXPLAIN, which it recurses
  into. COPY, PREPARE and EXECUTE are left alone. A PREPARE plans through
  `CreatePlan`, so the vehicle is bound at PREPARE and at EXPLAIN, and its bind
  must not execute.
- **How a DML node is handed over**: `GetNodeFromStatement` (opt:1825)
  yields the node, and `RemoteExecute(ClientContext&, unique_ptr<QueryNode>)`
  receives it. The returned ref is wrapped as `SELECT * FROM <ref>` (opt:1842).
  No result shape is imposed. Native DML returns one column named `Count`
  (bind_update.cpp:283), so the count vehicle should use that name.
- **Node classes** (`parser/query_node/`):
  - `UpdateQueryNode`: table, from_table, set_info (condition, columns,
    expressions), returning_list.
  - `DeleteQueryNode`: table, using_clauses, condition, returning_list.
  - `InsertQueryNode`: columns, select_statement, `on_conflict_info`,
    returning_list, `default_values`, column_order, `GetValuesList()`.
  - `MergeQueryNode`: target, source, join_condition or using_columns,
    actions, returning_list.
  - Any of these can appear as a CTE body.
- **INSERT** (opt:440-460): the rewriter pushes the SELECT alone when the
  target is in another catalog or when `SupportsPushdown(InsertQueryNode)` says
  no. **`INSERT … VALUES` reaches `SupportsPushdown` too**: the VALUES list
  belongs to no catalog. So VALUES, `DEFAULT VALUES`, ON CONFLICT, RETURNING
  and BY NAME each need an explicit no.
- **`EXECUTE_STATEMENT`** is per catalog. Claiming it sends every CREATE /
  DROP / ALTER of the catalog to `SupportsPushdown(SQLStatement)`; there is no
  CTAS-only claim.
- **`$n` parameters** are not refused by the rewriter (opt:1198-1222); we
  have to refuse them. Constant folding runs before `SupportsPushdown`.
- **Read-only is bypassed.** A rewritten DML binds as a SELECT, so
  `modified_databases` stays empty and `MetaTransaction::ModifyDatabase` never
  runs. ATTACH READ_ONLY and the one-writable-database rule are lost.
  - A better guard than the spec's: `TableFunctionBindInput::binder` →
    `GetStatementProperties().RegisterDBModify(...)` in the vehicle's bind.
    DuckDB then enforces both rules itself.
- **Changes since 62ee922db3**: `2e136b37f28` makes `StripCatalogName` drop
  only the catalog part of a column reference with three or more parts. The
  other commit is a rename. There is no API change for DML.
- **MERGE**:
  - The rewriter carries a MergeQueryNode whole (opt:531-561).
  - The generic `Catalog::PlanMergeInto` (plan_merge_into.cpp:301) plans each
    action through our `PlanUpdate` / `PlanDelete` / `PlanInsert`, refuses
    RETURNING itself, and needs `GetRowIdColumns`, which is our rowid key
    ladder.
  - **So MERGE probably runs today on a keyed table, untested.**
- **No reference implementation** of a DML `RemoteExecute` exists in the tree.

## 2. The extension's DML today

- **UPDATE / DELETE**:
  - Rowid VALUES-join batches of `min(500, 2000 / params per row)`, with
    inline literals sent as a SQL_BATCH. Spec 083 did not touch DML.
  - The buffers are `vector<vector<Value>>` (the per-value path).
  - `defer_execution_` buffers the whole statement inside a transaction and
    flushes it in Finalize.
  - The connection is a `MSSQLStatementConnection`: pinned in a transaction,
    otherwise one pool connection under the `LoadTransaction` bracket.
- **UPDATE / DELETE … RETURNING fail with an InternalException**
  (`Vector::Reference used on vector of different type`, measured
  2026-10-08). The plan returns one BIGINT and never reads `return_chunk`, and
  DuckDB's RETURNING projection over it fails. An InternalException
  invalidates the database. Fixed inside 080 (owner: no separate PR, no users
  on this line yet).
- **The token loop exists five times**:
  - UPDATE / DELETE / INSERT `ExecuteBatch`;
  - INSERT RETURNING's `MSSQLReturningParser`;
  - the reference loop, `MSSQLSimpleQuery`.

  Each DML copy hard-codes a 30 s timeout and carries the
  `mssql_test_fail_parse_after_tokens` lever. `ExecuteDmlBatch` does not exist.
- **`CollectSinkCatalogs`** (`table_scan/mssql_optimizer.cpp:853`) counts
  COPY, INSERT and CREATE TABLE, but not UPDATE or DELETE.
- **Keyless DML** is refused at bind in `BindUpdateConstraints`,
  `GetRowIdColumns` and `GetRowIdType`, and again in the plan hooks. #140 was
  closed by #364's text, not by code, and was reopened on 2026-10-08.
- **`mssql_dml_use_prepared`** is registered and read into `config` but used
  by nothing else. `EnsurePKLoaded` is a `D_ASSERT` since 084.
- **Pool of one**:
  - UPDATE in a transaction works by deferring (`transaction_single_connection_pool.test`).
  - In autocommit the scan and the batches compete for the single connection.
  - `BulkLoadSession::DeferAdoption` / `AdoptDeferred` (COPY, CTAS) already
    implement "take the connection at the first Sink".
- **No DML counters exist** under `MSSQL_COUNTERS`. `CountRemotePushdown` is
  the only pushdown counter.

## 3. The writer (079) and DML

- `Supports()` claims IS_REMOTE and EXECUTE_QUERY_NODE only.
  `SupportsPushdown(SQLStatement)` returns false. `WritePushdown` vetoes every
  node that is not a SELECT or a set operation.
- **`RemoteExecute` cannot decline a DML node.** Its fallback hands the node
  back as a `SubqueryRef(SelectStatement)`, and a DML node cannot be returned
  that way. **Every DML decision belongs to the dry run**: read-only, search
  path, parameters, nesting, renderability.
- **`PushesMoreThanScan` vetoes every non-SELECT.** The join threshold and
  `mssql_pushdown_min_rows` do not apply to DML, so DML needs its own path
  decided on renderability alone.
- **Writer**: there is no DML entry point. Needed:
  - `WriteUpdate` / `WriteDelete`, with relations always aliased (relation 0
    is the target) and `CollectRelations` / `WriteFrom` / `WritePredicate`
    reused;
  - a SET-value type rule (the operand's type must equal the column's);
  - `value_divergence` / `approximate` must veto, because a DML writes the
    value;
  - a veto on `UPDATE … FROM` unless every source row matches at most one
    target row (T-SQL picks an arbitrary match).
- **Count vehicle**:
  - Its bind can reuse 081's no-describe bind; its init cannot reuse
    `MSSQLScanInitGlobal`.
  - `MSSQLSimpleQuery` overwrites `rows_affected` on every DONE, so a trigger's
    count, or IDENTITY_INSERT's, can replace the statement's count. The count
    needs a rule (§ 4).
- **Invalidation after a pushed DML**: the statistics provider's row count
  for the table (`GetStatisticsProvider().InvalidateTable`). Do not use
  `InvalidateTableEntry`: its epoch bump would clear the describe cache and
  withhold publication. Today's shipped DML invalidates no statistics either.

## 5. Owner's decisions (2026-10-08)

- No table-valued parameters: a TVP needs `CREATE TYPE` rights, which cannot
  be assumed, and Fabric / Synapse portability is required. Stage through
  `#stage` + bulk load.
- RETURNING on UPDATE / DELETE is fixed inside 080, not in a separate PR.
- #140 reopened.
- MERGE is in scope for v0.3.0.
