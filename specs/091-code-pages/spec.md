# Spec 091: SQL Server code pages, generated tables and vectorized kernels

Status: **implemented in this PR** for the module: the generator and its data (D2, D3), the
tables (D4), the decode kernels (D5), the collation lookups (D9), the unit test, the fuzz harness
and two benchmarks. Branch `feat/091-code-pages` from main `4c65cfb`, 2026-11-06. **Follow-ups**
(Follow-ups, Tasks): the streaming form (D6), the encode direction (D7), representability (D8),
the live CI sample and the wire bytes (D10), the x86-64 and double-byte SIMD kernels. The DuckDB
wrapper the first draft put here is spec 092's, beside its first caller.

Consumers: spec 092 (the live read path; a draft, on this branch) and specs 085 / 086 (the backup
reader, open PR #526, branch `spec/085-090-backup-reader`). 085 / 086 are cited at PR #526's head
`7d65d00`, one commit past the `c9102bf` the first draft cited, by line, and by section where its
next push changes the text.

One module turns SQL Server's code-page bytes into UTF-8 on the client, from tables generated by
asking a SQL Server. Nothing calls it yet (`DATAMODEL.md:758-762`): no read or write path changes in
this PR. It serves two paths with different needs:
- the **backup reader** has no server to convert anything, so every code page, double-byte
  included, is decoded here (085 D7, 086 D9);
- the **TDS read path** still has the server. It takes the client-side transcode only where it is
  faster than the server's `CAST` to NVARCHAR, which the measurements below put at the single-byte
  pages (Benchmark; spec 092 D10).

## Problem

- A `char` / `varchar` / `text` value under a non-UTF-8 collation is bytes in the collation's code
  page. Until this module the extension had no table to decode them:
  - the catalog scan asks the server, `CAST(col AS NVARCHAR(n))`
    (`BuildReadExpression`, `src/catalog/mssql_column_info.cpp:567-570`);
  - a raw `mssql_scan` hands the bytes to a DuckDB VARCHAR verbatim (#224, documented and not
    enforced: `src/query/mssql_result_stream.cpp:944-990`).
- The backup reader has no server to ask. It decodes through this module (085 D7, 086 D9).
- The one other piece of code-page knowledge in the tree is `CodePageCanEncode` (#361,
  `src/catalog/mssql_code_page.cpp`). It is not a decoder:
  - its tables are sorted sets of the code points of bytes 0x80-0xFF, not byte -> code point maps
    (`mssql_code_page.cpp:10-12`, `:25-142`);
  - they were generated from Python's codecs (`:11`);
  - only 874 and 1250-1258 have one. 437, 850 and the four double-byte pages answer "cannot tell"
    for anything outside ASCII (`src/include/catalog/mssql_code_page.hpp:18-25`).
- Collation -> code page was known only from the server. The column metadata queries carry
  `COLLATIONPROPERTY(c.collation_name, 'CodePage')` (`src/catalog/mssql_metadata_cache.cpp:208`,
  `:240`), and the ATTACH query carries it for the database (`src/catalog/mssql_catalog.cpp:44-52`).
  - A raw scan's COLMETADATA has only the 5 wire bytes of the collation
    (`src/include/tds/tds_column_metadata.hpp:21-26`).
  - A backup has a 4-byte collation id per column (085 `spec.md:533-534`).

## What the tree, PR #526 and the server say

- **F1. The code pages.** Counted from the committed `tools/code_pages/data/collations.psv`: 5,540
  rows of `sys.fn_helpcollations()` on SQL Server 2025 (D3). It succeeds the 085 research's
  `tools/collations.psv` (`research-experiment.md:297`), which gives the same counts; 085 now cites
  this one (085 `spec.md:569-575`).

  | code page | kind | collations | reached through |
  |---|---|---:|---|
  | 437 | single byte (OEM) | 6 | `SQL_Latin1_General_CP437_*` only |
  | 850 | single byte (OEM) | 14 | `SQL_` only: `CP850`, `1xCompat`, `AltDiction`, `Scandinavian` |
  | 874 | single byte | 52 | `Thai`, `Thai_100` |
  | 1250-1258 | single byte | 586 / 482 / 894 / 57 / 156 / 54 / 190 / 164 / 52 | Windows and `SQL_` |
  | 932 | double byte | 206 | `Japanese*` |
  | 936 | double byte | 172 | `Chinese_PRC*`, `Chinese_Simplified_*` |
  | 949 | double byte | 86 | `Korean*` |
  | 950 | double byte | 274 | `Chinese_Taiwan*`, `Chinese_Traditional_*`, `Chinese_Hong_Kong_Stroke_90` |
  | 65001 | UTF-8 | 1,585 | `*_UTF8`, SQL Server 2019+ |
  | 0 | Unicode-only | 510 | `nvarchar` only; no `varchar` can carry one |

  The double-byte counts match 086 D9 (`spec.md:99`). `COLLATIONPROPERTY` documents four
  properties, `CodePage`, `LCID`, `ComparisonStyle` and `Version`, and lists no code page values
  (Microsoft Learn, *COLLATIONPROPERTY*).
- **F2. The wire collation** is 20 bits of LCID, 8 of flags, 4 of version, then the SortId byte
  (`tds_column_metadata.hpp:43-46`), parsed for the string types at
  `src/tds/tds_column_metadata.cpp:314-331` and for `text` / `ntext` at `:403-421`. fUTF8 is
  `0x04000000` in the word (`tds_column_metadata.hpp:61-63`). LCID alone does not name the page:
  `SQL_Latin1_General_CP1_CI_AS` (1252) and `SQL_Latin1_General_CP1251_CI_AS` (1251) both report
  LCID 0x0409 and differ only by SortId, 52 against 106 (`DATAMODEL.md:689-692`).
- **F3. The on-disk id is another encoding.** `Latin1_General_CI_AS` is `0x00D00409` on the wire
  (`tds_column_metadata.hpp:53-54`) and `0x0000D008` as its `CollationId`; `Cyrillic_General_CI_AS` is
  `0x00D00419` against `0x0000D015` (`collations.psv`).
  - `CollationId` is `COLLATIONPROPERTY(name, 'CollationId')`: not among the documented four (F1),
    but answered by SQL Server 2025 for all 5,540 collations, each a distinct value (F16). The psv
    calls the column so (PR #526, `specs/085-backup-reader-core/research/research-experiment.md:33`).
  - Its low bits are an internal index, not the LCID: `Albanian_BIN` is `0x00010018`, LCID 0x041C.
    A `SQL_` collation keeps its SortId in the top byte (F16).
  - 085's rule: a collation is UTF-8 iff `id >> 24 == 0` and `id & 0x80` (085 `spec.md:572-573`).
    It holds over the committed file too, with no exception.
  - The LCID column is 20 bits wide as on the wire: 642 collations carry sort bits above 0xFFFF
    (`Chinese_PRC_Stroke_90_*`: 0x20804), none above 0xFFFFF.
- **F4. Python is not the server.** Python's codecs leave 110 bytes of 874 / 1250-1258 undefined,
  and the server maps every one of them (F13). These are exactly the gaps in #361's tables:
  `CP1252_HIGH` holds 123 = 128 - 5 code points (`mssql_code_page.cpp:60`), `CP874_HIGH` 97 (`:25`).
- **F5. The server best-fits on the way into a code page.** The staged MERGE stages a code-page
  column as `nvarchar(max)` because, as `varchar`, "'Łukasz' would match 'Lukasz'"
  (`src/dml/merge/mssql_merge_rewrite.cpp:71-75`).
- **F6. Values are whole before any kernel runs.**
  - The read path assembles a PLP value chunk by chunk into staging (`AppendPlp`,
    `src/codec/staging/row_stager.cpp:241-270`). It is handed a row only once the whole row is
    buffered (`:210-211`).
  - 085 rebuilds a LOB value node by node and checks its length (085 `spec.md:612`).
  - So a double-byte character split across PLP chunks reaches no kernel split, on either path.
- **F7. The kernels this one is measured against.**
  - Code-page bytes go to the binary kernel today: one allocation and one memcpy per column
    (`src/codec/binary_codec.cpp:89-136`; arms at `src/codec/staging/column_ops.cpp:441-457`).
  - UTF-16 goes to `string::DecodeChunkFromStaging` (`src/codec/string_codec.cpp:928-937`, its body
    `DecodeChunkImpl` at `:493-580`): one `simdutf::convert_utf16le_to_utf8` per column, at a
    worst-case allocation of `units * 3` (`:133-140`), with a free pure-ASCII verdict (`:531-543`).
- **F8. simdutf is pinned at 6.1.1** (`vcpkg.json` overrides). It has `validate_ascii`,
  `validate_utf8` and `convert_latin1_to_utf8` (its `simdutf/implementation.h:205`, `:161`, `:452`,
  as vcpkg installed it in a local release build). The module does not link it (D4).
- **F9. A DuckDB string holds at most `UINT32_MAX` bytes.** `string_t::MAX_STRING_SIZE`
  (`duckdb/src/include/duckdb/common/types/string_type.hpp:31`), and a larger `EmptyString` throws
  `OutOfRangeException` (`string_heap.hpp:66-72`, at the pin `d54cbbe3df1`). A column's staged
  payload in one chunk can reach 2047 MB (`src/include/codec/staging/column_staging.hpp:67-75`): the
  32 MB budget closes a chunk only after the row that crosses it (`:77-84`,
  `src/query/mssql_result_stream.cpp:351-353`).
- **F10. DuckDB's encoding API is CSV-shaped.** `encode_t` takes a `CSVEncoderBuffer &`
  (`duckdb/src/include/duckdb/function/encoding_function.hpp:25-29` at the pin).

**Measured on SQL Server 2025 (17.0.4075.5, Enterprise Developer Edition, 64-bit;
`tools/code_pages/data/provenance.txt`), 2026-11-06**, by the generator (D2). Every count below is
of the committed `tools/code_pages/data/` (D3), recounted from the files.

- **F11. `COLLATE` converts, it does not reinterpret.** On a varchar expression it converts the
  characters from the source's code page: `CONVERT(varchar(2), 0x82A0) COLLATE Japanese_CI_AS` reads
  `??` as nvarchar, and `CONVERT(varchar(1), 0xE4) COLLATE Cyrillic_General_CI_AS` reads `a`, the
  best fit of 1252's `ä` (`tools/code_pages/generate.py:15-17`). Assignment into a column of another
  code page converts likewise. So the generator uses neither a `COLLATE` nor a collated column to
  read bytes (D2).
- **F12. What works: one database per code page.** In a database whose default collation is of the
  page (`CREATE DATABASE <db> COLLATE <collation>`), a probe run in its context
  (`EXEC <db>.sys.sp_executesql N'...'`) reads bytes under that page:
  `CONVERT(nvarchar(n), CONVERT(varchar(n), <binary>))` (`generate.py:76-80`). The collations, two a
  page, of different kinds or versions (`generate.py:52-69`):

  | page | first | second |
  |---|---|---|
  | 437 | `SQL_Latin1_General_CP437_CI_AS` | `SQL_Latin1_General_CP437_BIN` |
  | 850 | `SQL_Latin1_General_CP850_CI_AS` | `SQL_Scandinavian_CP850_CI_AS` |
  | 874 | `Thai_CI_AS` | `Thai_100_CI_AS` |
  | 932 | `Japanese_CI_AS` | `Japanese_XJIS_140_CI_AS` |
  | 936 | `Chinese_PRC_CI_AS` | `Chinese_PRC_90_CI_AS` |
  | 949 | `Korean_Wansung_CI_AS` | `Korean_90_CI_AS` |
  | 950 | `Chinese_Taiwan_Stroke_CI_AS` | `Chinese_Taiwan_Stroke_90_CI_AS` |
  | 1250 | `Czech_CI_AS` | `SQL_Czech_CP1250_CI_AS` |
  | 1251 | `Cyrillic_General_CI_AS` | `SQL_Latin1_General_CP1251_CI_AS` |
  | 1252 | `Danish_Norwegian_CI_AS` | `SQL_Latin1_General_CP1_CI_AS` |
  | 1253 | `Greek_CI_AS` | `SQL_Latin1_General_CP1253_CI_AS` |
  | 1254 | `SQL_Latin1_General_CP1254_CI_AS` | `Turkish_100_CI_AS` |
  | 1255 | `SQL_Latin1_General_CP1255_CI_AS` | `Hebrew_100_CI_AS` |
  | 1256 | `SQL_Latin1_General_CP1256_CI_AS` | `Arabic_100_CI_AS` |

  | 1258 | `Vietnamese_CI_AS` | `Vietnamese_100_CI_AS` |

  Each page: 256 single bytes, and on a double-byte page also the 128 x 256 pairs whose first byte
  is >= 0x80: 12 x 256 + 4 x 33,024 = 135,168 rows a collation. The first prototype, one collation
  a page, took about 10 s through the extension's `mssql_scan`.
- **F13. Single-byte pages.** Every byte reads as exactly one code point, never none or two, and
  0x00-0x7F as themselves. 110 bytes differ from Python's codecs, each one a byte Python leaves
  undefined: 874 31, 1250 5, 1251 1, 1252 5, 1253 17, 1254 7, 1255 23, 1257 12, 1258 9, and none on
  437, 850 or 1256. On every byte Python defines, the two agree. Examples: 1252 0x81 -> U+0081,
  0x80 -> U+20AC.
- **F14. Double-byte pages.**
  - Lead bytes: 932 has 60 (0x81-0x9F, 0xE0-0xFC), 936 / 949 / 950 126 each (0x81-0xFE).
  - A lead byte alone reads as an empty string: the server drops it.
  - A lead byte and a trail 0x01-0xFF read as exactly one code point: a character, or the page's
    replacement (`?` on 936 / 949 / 950, U+30FB `・` on 932: 932 `81 01` and `81 20` -> U+30FB).
  - A lead byte and 0x00 read as the replacement, then U+0000: the 0x00 is not consumed.
  - A pair whose first byte is not a lead byte reads as the two bytes read alone; when its second
    byte is a lead byte, that one reads as nothing (`emit_tables.py:102-106`).
  - 932's single bytes: 0x5C -> U+005C, 0x80 -> U+0080, 0xA0 -> U+F8F0, 0xA1-0xDF -> U+FF61-U+FF9F,
    0xFD-0xFF -> U+F8F1-U+F8F3. Pairs: 0x82A0 -> U+3042, 0x8140 -> U+3000.
  - Against Python: of each page's 33,024 probed inputs Python refuses 9,896 (932), 11,105 (936),
    15,848 (949) and 19,144 (950), and the server reads every one. On the inputs Python accepts the
    two agree, but for 249 pairs of 950 that Python reads as other characters: the server reads
    each as a private-use code point (0xC6A1 -> U+F6B1, where Python reads `ヾ`).
  - So a double-byte page is a table of lead x trail (60 x 256 or 126 x 256, entry 0 the
    replacement for a trail 0x00) plus two rules: trail 0x00, and a lone lead at the end.
  - Many to one: on 932, 396 characters are each read from two or more sequences, 794 in all (NEC /
    IBM duplicates); on 950, 10 characters from 20. Counted without the replacement.
- **F15. The output bound is 3 UTF-8 bytes per input byte, on every page.** No answer holds a
  surrogate (`emit_tables.py:51-60` refuses one), so every code point is in the BMP (at most 3
  UTF-8 bytes). Single bytes reach 3: 437 0x9E -> U+20A7, 1252 0x80 -> U+20AC, 932 0xA0 -> U+F8F0
  and its half-width katakana, 936 0x80 -> U+20AC, 949 / 950 0xFF -> U+F8F7 / U+F8F8. A pair reads
  as at most 3 bytes for 2; lead + 0x00 consumes the lead alone and writes at most 3 for it; a lone
  lead writes none. `MAX_UTF8_PER_BYTE = 3` (`src/include/codec/code_page/code_page.hpp:78-81`).
- **F16. Collation -> code page needs no COLMETADATA.** `COLLATIONPROPERTY(name, 'CollationId') >>
  24` is the SortId: `0x3400D008` -> 52 for `SQL_Latin1_General_CP1_CI_AS`, `0x6A00D008` -> 106 for
  `SQL_Latin1_General_CP1251_CI_AS`, the SortIds COLMETADATA carries (F2).
  - Over all 5,540 collations the page is determined by the SortId when it is non-zero (75
    SortIds, 77 collations), and by (LCID, `_UTF8`) otherwise (161 keys; 12 of them Unicode-only,
    page 0). No key names two pages.
  - It does not depend on `Version`: 57 of the 161 keys span several versions, with one page each.
  - `_UTF8` in the name and page 65001 coincide on every row. The 5,540 `CollationId`s are distinct.
- **F17. The reading belongs to the code page, not the collation.** On all 16 pages the second
  collation (F12) reads every byte and pair exactly as the first: the 16 `cpNNN.alt.psv` files are
  byte-identical to their `cpNNN.psv`. The 1,600 seeded strings (400 a double-byte page, 3-12
  bytes) read whole by the server agree with F14's rules applied left to right. In 98 / 275 / 267
  / 290 of them (932 / 936 / 949 / 950) a pair whose trail is itself a lead byte is followed by
  more bytes: the case a pair's answer alone cannot settle (consumed as one pair, or the lead read
  alone and the trail dropped), which the first draft meant to ask with triples.

## Decisions

- **D1: the tables come from SQL Server itself.** A generator in `tools/code_pages/` asks a server
  for every answer (D2). The answers are committed (D3); a CI sample against a live server is a
  follow-up (D10). Rejected:
  - iconv / `MultiByteToWideChar`: they differ per platform, e.g. glibc's CP932 against Windows'
    (owner's survey, **to verify**), and the extension builds on Linux, macOS, MSVC and MinGW;
  - ICU: 25-30 MB of data, and its double-byte mappings differ from Windows' in places (owner's
    survey, **to verify**);
  - DuckDB's `encodings` extension: its API is CSV-shaped (F10). It is a separate extension that is
    not built on MinGW / WASM and is ICU-derived (owner's survey, **to verify**). The tests may use
    it as a cross-check, never as the source;
  - Python's codecs: 110 bytes undefined that the server maps (F13), every invalid double-byte
    sequence refused, and 950's 249 pairs read otherwise (F14).

  Invalid double-byte sequences then come out exactly as the server's `CAST` makes them, because
  that is what the table holds.
- **D2: the generator, as built.**
  - **Method (F11, F12).** Two scratch databases per code page, `mssql_cpgen_<cp>` and
    `mssql_cpgen_<cp>_alt`, created `COLLATE` the page's first and second collation
    (`generate.py:156-157`, `:181`), and every probe run in one through
    `EXEC <db>.sys.sp_executesql N'...'` (`:182`). Never a `COLLATE` or a collated column to read
    bytes: both convert (F11).
  - **Tools: Python over the extension's own CLI; no C++ tool.**
    - `tools/code_pages/generate.py` writes the whole run as one DuckDB script (ATTACH,
      `mssql_exec` for the databases, `COPY (SELECT i, o FROM mssql_scan(...) ORDER BY i) TO ...`
      for the answers; `:160-195`) and runs it on the release build's CLI (`:222-226`, `:233-235`).
      F12 showed `mssql_scan` suffices; the tables need no TDS access of their own.
    - `tools/code_pages/emit_tables.py` checks the answers (below) and writes the C++ tables.
    - The draft's `wire_keys.cpp`, which was to read every collation's 5 wire bytes, is not built
      (Follow-ups).
  - **Asked per page** (`generate.py:83-87`, `:109-138`):
    - every byte 0x00-0xFF and, on a double-byte page, every pair whose first byte is >= 0x80,
      under both collations (F12);
    - on a double-byte page, 400 distinct seeded strings of 3-12 bytes, as `varchar(16)` read into
      `nvarchar(16)` (`:136-138`). The PRNG is splitmix64, seeded per page (`:97-113`), so the set
      is the same on every Python version. The bytes are weighted toward what a double-byte page
      reads specially: 40 % lead range 0x81-0xFE, 20 % trails 0x40-0x7E, 10 % 0x00, 10 % the
      edges 0x80 / 0xA0 / 0xFD-0xFF, 20 % any (`:114-132`).
  - **Asked once:** every `sys.fn_helpcollations()` row with `COLLATIONPROPERTY` `CollationId`,
    `LCID`, `CodePage` and `Version` (`:88-92`), and the server's `ProductVersion` and edition
    (`:93-94`).
  - **Transport.** Every answer travels as hex text (`CONVERT(varchar(n), <varbinary>, 2)`,
    `:76-80`), so no decode on the client touches the data.
  - **Guards.** The generator's own SQL is not trusted, and neither is the CLI:
    - the CLI can exit 0 on a runtime error, so every output file must hold its row count (256 /
      33,024 / 400 / at least one collation / one provenance row), or the run fails naming the
      file (`:246-252`, expected counts at `:183`, `:188`, `:193-194`);
    - the run writes into a temporary directory and moves the files into `data/` only when every
      one is complete (`:239-241`, `:260-261`), so a failed run leaves the committed data as it was;
    - the scratch databases are dropped in a `finally`, failed run or not, by a cleanup script
      without `-bail`, so every `DROP` is tried (`:198-204`, `:253-259`; `KEEP_DATABASES=1` keeps
      them);
    - the DSN goes to the CLI on stdin only, never in argv or a file (`:222-226`; the Makefile
      passes it through the environment, `Makefile:867-871`), and every error is printed through
      `redact()`: the DSN as given and as quoted into the script, `password=` / `pwd=` values, a
      URL's password (`generate.py:146-153`);
    - a collation `PAGES` names that the committed `collations.psv` does not give that page stops
      the run before it starts (`:207-219`, `:237`).
  - **Assertions** (the emitter's, `emit_tables.py:7-23`; a failure stops it and names the case):
    - bytes 0x00-0x7F read as themselves on every page (`:87-88`). The ASCII steps (D5) rely on it;
    - no answer holds a surrogate (`:51-60`); a single-byte page reads every byte as one code point
      (`:89-92`; a lead byte is a byte 0x80-0xFF that reads as nothing);
    - a double-byte page follows F14's rules, pair by pair (`:93-115`), and its strings read as
      the rules applied left to right (`:118-133`, `:149-165`). Together that is the 3x bound (F15);
    - each second collation reads every byte and pair as the first (`:136-146`, F17);
    - the collations: names are plain identifiers, versions fit a byte, `CollationId`s distinct,
      no two names that differ only in case, a SortId names one page and so does (LCID, `_UTF8`)
      (`:168-194`, F16); the pages the collations name, but 0 and 65001, are exactly the pages
      probed (`:215-218`).
    - A missing `.alt.psv` or `.strings.psv` is reported, not fatal (`:219-231`): the tables can be
      emitted from the primary data of an older run. All 20 are committed.
  - **Not asked**, against the first draft: the triples (F17's strings settle their question);
    an `EXCEPT` over every other collation of a page (one second collation of another kind or
    version instead, F17); representability (D8); the wire bytes; runs on 2022 and 2019 (D10).
- **D3: the committed outputs.** All under `tools/code_pages/data/`, sorted (`ORDER BY i`,
  `generate.py:169`; collations by name, `:189`), with no date and no server version in any data
  file:
  - `cp<NNN>.psv`: `in_hex|out_utf16le_hex`, every byte and, on a double-byte page, every pair
    (F12): 135,168 rows;
  - `cp<NNN>.alt.psv`: the same under the page's second collation, evidence only (F17): 135,168;
  - `cp<NNN>.strings.psv` (double-byte pages): the strings, same columns: 4 x 400;
  - `collations.psv`: `name|collation_id|lcid|code_page|version`, 5,540 rows. It replaces the
    research's `tools/collations.psv` (F1); 085 names this file (`spec.md:125`, `:570`), 086 none;
  - `provenance.txt`: `17.0.4075.5|Enterprise Developer Edition (64-bit)`, the one place the
    server is named.

  277,476 rows, about 3 MB. Emitted from them: `src/codec/code_page/code_page_tables.cpp` (16,543
  lines), plain integer arrays (MSVC limits string literals, not array initializers) between
  `clang-format off` / `on`. `make code-pages-generate` (needs a server, builds the release CLI
  first) asks again and re-emits; `make code-pages-tables` (no server) re-emits from `data/`
  (`Makefile:869-874`). The PR diff of `data/` is what a reviewer reads. There is no separate
  fixture: the unit test replays `data/` (Tests 1). A rerun on the same build should leave an
  empty diff, `provenance.txt` included; that a second run does is not shown yet (Acceptance).
- **D4: one module, DuckDB-free.** `src/codec/code_page/code_page.cpp` (kernels and lookups) and
  the emitted `code_page_tables.cpp`, headers `src/include/codec/code_page/code_page.hpp` and
  `code_page_tables.hpp`. Namespace `duckdb::mssql::codec::code_page`, as the family modules
  (`src/codec/binary_codec.cpp:44-47`), the generated data in a nested `tables`
  (`code_page_tables.hpp:21-25`).
  - It includes nothing from DuckDB and does not link simdutf (`code_page.hpp:42-43`,
    `code_page_tables.hpp:11-13`), and builds as C++11 (`Makefile:865`), the standard the extension
    builds at (CLAUDE.md, *ODR*). So the unit test links the module alone (`Makefile:876-886`) and
    the fuzz harness runs in the per-PR ClusterFuzzLite lane (Tests 2).
  - Both sources are in the extension's source list (`CMakeLists.txt:143-145`).
  - The DuckDB wrapper (a staging-shaped chunk entry and a per-value entry publishing `string_t`)
    is spec 092's (its D2), where its first caller is.
  - `src/catalog/mssql_code_page.cpp` stays, and `CodePageCanEncode` answers from #361's tables
    until D8 (`code_page.hpp:65-70`).
- **D5: the decode kernel, as built.** One call per column per chunk, never per value: the
  repository's rule, and 085 D7's. One pass over the input and one sequential write of the output,
  with no validation pass in front: every byte sequence has an answer, the server's, and 0x00
  decodes to U+0000, as stored.
  - **Output in the caller's buffer.** `Utf8Bound(n) = 3n + STORE_SLACK` bytes, `STORE_SLACK = 16`;
    a decode writes at most `STORE_SLACK` bytes past the length it returns (the 16-byte stores, the
    4-byte packed store; `code_page.hpp:38-40`, `:75-86`). Sizing is the caller's: past ~1.43 GB of
    payload `3n` exceeds a DuckDB string (F9), and `ExactUtf8Length` gives the size to allocate
    (`code_page.hpp:128-131`). The switch and the refusal of a column no DuckDB string can hold are
    spec 092's.
  - **No heap allocation in a call.** The per-page NEON planes and the two compaction tables are
    built once, in function-local statics (`code_page.cpp:249-252`, `:278-281`, `:341-344`: one
    vector of 16 planes, allocated at the first call, thread-safe as any function-local static).
    A page is always an entry of `tables::CODE_PAGES`, found by `CodePageTable::index`
    (`code_page_tables.hpp:30-33`, `code_page.hpp:88-93`), never a copy.
  - **Entries** (Surface): `DecodeToUtf8` (one string), `DecodeValues` (values staged back to
    back, the read path's staging or a backup page's records: offsets and lengths, `src_size`
    bounding every read so a short value may read ahead into the next, never past the buffer; a
    lead byte never runs across values), `DecodeToUtf16` (stage 1 of a two-stage decode),
    `CopyAscii`, `ExactUtf8Length`. `DecodeValues` takes no validity: the caller passes the values
    it wants, a NULL as length 0 or not at all.
  - **A single-byte page on arm64: the NEON kernel** (`DecodeNeon`, `code_page.cpp:476-596`), 32
    bytes a step as two 16-byte blocks, two independent lookup chains so their latencies overlap.
    A step takes the first tier that holds:
    1. **ASCII store.** `vmaxvq(v0 | v1) < 0x80`: the two blocks are stored as they are
       (`:495-501`).
    2. **Run arithmetic.** The page's longest run of bytes whose code point is byte + delta, all
       below U+0800, at least 16 bytes (`BuildPlanes`, `:294-315`): 1251 C0-FF -> U+0410-U+044F,
       1252 A0-FF -> U+00A0-U+00FF. A step whose non-ASCII bytes all lie in it needs no lookup:
       second byte `vbsl(0x3F, low, 0x80)`, first byte two shift-right-and-accumulates (`vsra`)
       onto the run's lead (`RunPlanes`, `:409-422`); its 2-byte masks are the ASCII masks
       inverted (`:513-518`). A run that ends at 0xFF is, with ASCII, one cyclic interval
       `[run_lo, 0x7F]`, so "ASCII or in the run" is one subtract and one compare
       (`:386-389`, `:506-509`).
    3. **The 80-BF window** (1251, 1252: their run covers C0-FF, `:390-393`, `:372-374`). Every
       byte outside the run lies in 80-BF, so one 64-entry `vqtbx4q` per plane, with the run's
       arithmetic as `vqtbx`'s default, decodes any step (`:519-538`). 3-byte packing is chosen
       per block: only the block that holds a 3-byte character takes it (`:529-536`).
    4. **Generic TBX planes** (`:539-553`): first and second UTF-8 byte planes, two `vqtbx4q` each
       (the 80-BF and C0-FF halves); a step holding a 3-byte character takes `Block3`, a third
       plane (`:469-474`).
    5. **Packing.** `Pack2` is simdutf's UTF-16 -> UTF-8 compaction applied to code pages: 8
       characters as interleaved (first, second) byte pairs, a 256-entry shuffle table indexed by
       the 2-byte-lead mask (`:226-247`, `:433-440`; the four 8-lane masks of a step in one go,
       `Masks4`, `:396-402`). `Pack3` is simdutf's 1/2/3-byte packing: 4 characters as 32-bit lanes,
       a 2-bit length code each, a second 256-entry table (`Compaction3`, `:254-276`, `:442-467`).
    - The tail: one 16-byte block (`:566-589`), then byte by byte from the packed table
      (`:590-594`).
    - `DecodeNeon` is always inlined into both callers, so the kernel's constants stay in
      registers across `DecodeValues`' loop: measured 3-5 % on 20-60-byte values (`:486-489`).
  - **Everything else: the scalar `DecodeRun`** (`code_page.cpp:138-192`): a double-byte page; a
    single-byte page on x86-64 or with no SIMD; a value under 32 bytes in `DecodeValues`
    (`NEON_MIN_VALUE`, `:598-601`, `:613`). A 16-byte ASCII step (one load, one test of the high
    bits, one store: SSE2 `movemask`, NEON `shrn`, or two SWAR words, `FirstHighByte`, `:58-91`)
    alternates with a table step for the other bytes: UTF-8 from the page's packed 1 KB table
    (24 bits of UTF-8, its length on top), one 4-byte store, advancing by the length with no branch
    on it (`:185-188`). A double-byte lead byte reads its row of the pair table (2-byte code
    points, encoded to UTF-8 arithmetically, `EncodeBmp`, `:117-132`); F14's rules are the
    kernel's: a lead byte at a value's end writes nothing (`:173-176`), a trail 0x00 is not
    consumed (`:179-180`). No intrinsic is runtime-dispatched: SSE2 and NEON are the baselines of
    x86-64 and AArch64 (`code_page.hpp:28-32`, `code_page.cpp:9-19`; `MSSQL_CODE_PAGE_PORTABLE` forces
    the SWAR form).
  - **Stage 1, `DecodeToUtf16`** (`:665-741`): a single-byte page on NEON looks the code unit's low
    and high byte up in two more planes, ASCII passing through `vqtbx` with no branch
    (`:669-682`); elsewhere ASCII blocks widen by SIMD and the other bytes by the table
    (`:684-696`). A double-byte page follows `DecodeRun`'s structure. It writes nothing past
    `dst + n` (`code_page.hpp:109-115`).
  - **`CopyAscii`** (`code_page.cpp:810-825`, `:621-644`): 64 bytes a step, test and copy in the
    same loads, returning the ASCII prefix. `DecodeToUtf8` and `DecodeValues` do not call it: it is
    the entry for a caller that tries the all-ASCII chunk first (spec 092 D12).
  - **`ExactUtf8Length`** (`code_page.cpp:743-781`): `DecodeRun`'s loop, counting instead of storing.
  - **Trim is not the module's.** A `char(n)` is trimmed of trailing U+0020 of the OUTPUT by the
    consumer (092 D3), never of the input: an invalid `[lead, 0x20]` is one pair to the server (932
    `81 20` -> U+30FB, F14), and trimming the input first would leave a lone lead, which reads as
    nothing.
  - **Measured and rejected** (`make bench-code-page`, `make bench-code-page-tiers`, M4 Max):
    - two passes, `validate_ascii` then a `memcpy` (the bench's `2-pass`), lose to the fused ASCII
      step on every workload; they won only against the very first fused draft;
    - a blocked two-stage decode (stage 1 into a scratch block, stage 2 after it, block by block)
      gave nothing over the whole-payload two-stage on M4;
    - removing the all-ASCII step's test (tier 1) slows the latin workload by 40 %;
    - packing each 8-character half by its own 3-byte verdict gave nothing: the branch costs what
      the shuffle saves (`code_page.cpp:428-430`); the verdict is per 16-byte block;
    - branch mispredictions between tiers do not matter: a 50/50 mix of ASCII and Cyrillic-word
      steps costs 1.64 ns a step in ABAB order and 1.63 in random order (Benchmark).
  - **Not built, against the first draft:** the trim template parameter (above); the validity
    words (above); the Latin-1 variant for 1252 through `simdutf::convert_latin1_to_utf8` (the run
    tier is the same arithmetic inside the kernel's step, with no second path to dispatch to; not
    measured); exact sizing below the threshold (the consumer's, not measured).
- **D6: deferred to the write-path follow-up: the streaming form.** Both known consumers assemble a
  value whole before any kernel runs (F6), so no lead byte has to be carried between pieces. A
  consumer that cannot hold a value, such as a `varchar(max)` value of up to 2^31 - 1 bytes decoded
  while it arrives, would need a `DecodeState` holding one pending lead byte, equal to the batch
  form at every split point. `DecodeValues` ends every value where its length says
  (`code_page.hpp:117-124`).
- **D7: deferred to the write-path follow-up: the encode table and `EncodeValues`.**
  - Consumer (d) needs, per BMP code point, the bytes the server stores (best fit or `?`, F5), in
    two modes: `AsServer`, the server's conversion, and `Refuse`, which stops at the first character
    that does not round-trip so a write path can refuse by name. Its generation and kernel are the
    follow-up's.
  - Its fuzz oracle is `decode(encode(decode(x))) == decode(x)`, not `encode(decode(x)) == x`: on
    932 and 950 several sequences read as one character (F14), and the server's encode gives one of
    them.
- **D8: follow-up: representability from the server, double-byte pages included.**

    back to `c`. The generator is to ask it of every BMP code point outside the surrogates, in the

  - `CodePageCanEncode` (`mssql_code_page.cpp:174-231`) then answers from it for every page: 437,

  - **Answers that change**, each to be listed in that PR with the generator's evidence:

  - **The values** (`code_page.hpp:61-73`): `CODE_PAGE_UNICODE_ONLY = 0` (what `COLLATIONPROPERTY`

## D5a — kernels specialised to a code page

The code page of every column is known exactly (COLMETADATA on the TDS path, the catalog in a
backup), so the kernel is chosen once per call, by the page (`DecodeNeonFor`), and the frequent
pages get their own: their run's arithmetic with literal constants, their exceptions in the
smallest window that holds them, and no page flags in the loop.
- **1252**: A0-FF read as Latin-1, so the UTF-8 is `C2` / `C3` (`vsraq_n_u8(0xC0, byte, 6)`)
  then `0x80 | (byte & 0x3F)`; every exception (the euro sign, the quotes, dashes and ellipsis,
  Œ Š Ž ...) lies in 80-9F: a 32-entry, two-register `vqtbx2q` per plane.
- **1251**: C0-FF read as U+0410-U+044F, so `D0` / `D1` (byte >= F0) then
  `0x80 | ((byte + 0x10) & 0x3F)`; every exception (Ё ё Ђ ... № and the typography) lies in 80-BF:
  the 64-entry half of the planes.
- **874**: A1-FB except DB-DE read as U+0E01-U+0E5B, three bytes each, all arithmetic (`E0`,
  `B8` / `B9`, `0x80 | ((byte + 0x20) & 0x3F)`); a block of Thai letters alone (Thai puts no space
  between words) is three planes interleaved by one `vst3q_u8`, 48 bytes, with no packing at all.
- A block a specialised kernel does not cover, and the tail under 32 bytes, take the generic kernel.
An analysis of the server's data (each page's dominant delta, its holes, where its exceptions
fall) picked them and names the next candidates: 1253 (Greek, delta +0x2D0 over B4-FE, holes
B5 B6 B7 BB BD D2) and 1254 / 1258 (Latin-1 with a few holes); 1250, 1257, 1256, 437 and 850 scatter
their letters and stay on the generic tables.

## Benchmark

`make bench-code-page` (`test/cpp/bench_code_page.cpp`, against the release simdutf,

module alone, `Makefile:888-892`). Manual, not in CI. Both interleave every way within each round,
the house rule, and report the median of 9 rounds; `bench-code-page` first compares every way's
output with `direct`'s, byte for byte, and aborts on a difference (`bench_code_page.cpp:237-249`).

**Per value, 2048 values a chunk, M4 Max.** `direct` is this module's `DecodeToUtf8` over the
whole payload (the NEON kernel on a single-byte page); `utf16` is
`simdutf::convert_utf16le_to_utf8` over the same text as UTF-16LE, what the read path runs today
after the server's `CAST`. Client CPU only: the server's CAST and the doubled wire bytes are not in
it (`bench_code_page.cpp:264`).

## Follow-ups

1. **x86-64 SIMD, single-byte pages.** Today a single-byte page on x86-64 takes `DecodeRun`: the
   16-byte SSE2 ASCII step and a scalar table step for every other byte, about 1 GB/s on
   non-ASCII text. SSE2 has no 128-entry byte shuffle (`pshufb` is SSSE3 and indexes 16), so NEON's
   `vqtbx4q` planes have no baseline equivalent. Planned: AVX-512 VBMI / VBMI2 (`vpermi2b` looks a
   byte up in 128 entries, `vpcompressb` packs); AVX2 with the run arithmetic (no lookup) and
   `pshufb` compaction as simdutf's AVX2 UTF-16 -> UTF-8 does, the table steps scalar; runtime
   dispatch, since neither is the x86-64 baseline the extension builds for. Measured on real x86
   in CI: the M4 numbers do not transfer. Spec 092's default on x86-64 waits for it or is measured
   on its own (092 D10).
2. **Double-byte SIMD.** Today `DecodeRun<true>`: about 11.6x simdutf's cost on Japanese
   (Benchmark). The TDS path does not need it (092 keeps the server's CAST for double-byte pages);
   the backup reader does (Consumers c). Planned: the pair boundaries by SIMD (a byte that cannot
   be a lead ends a run; inside a run of bytes that can, leads and trails alternate from its start,
   so the odd/even position in the run marks the pairs), the lookups scalar (a 64 KB pair table
   fits no shuffle). Meanwhile a branchless scalar stage 1 and simdutf's UTF-16 -> UTF-8 as stage 2
   (the bench's `2-stage`), its scratch a stack-allocated block rather than a heap buffer of n
   units.
3. **The encode direction and `CodePageCanEncode` from the same tables** (D7, D8): the generator's
   representability probe and encode answers, the bitsets, `CodePageCanEncode` over them,
   `src/catalog/mssql_code_page.cpp` removed, the #361 answer diff, the CLAUDE.md
   `mssql_scan_parameterize_filters` row (`CLAUDE.md:213`, "874 and 1250–1258") and
   `DATAMODEL.md:700-705`.
4. **The CI oracle sample against a live server** (D10), with the wire bytes of every collation
   (the draft's `wire_keys`, through `SimpleQueryResult`; D9's "to verify") and the 2022 / 2019
   runs and their diff against 2025.
5. **The streaming form** (D6), with the write path.
6. **A seed corpus** for `fuzz_code_page`: `fuzz/corpus/code_page/` does not exist, so `build.sh`
   zips none (`fuzz/build.sh:270-275`) and `run.sh` seeds three bytes (`fuzz/run.sh:47`).

## Risks

- **An answer that differs between server versions** would make the client disagree with the
  server it reads. The tables come from 2025 alone until the D10 sample runs on 2022. Azure SQL is
  not sampled (the Azure lane is manual).
- **A collation newer than the tables** misses (`CODE_PAGE_NOT_FOUND`, D9) and falls back to the
  consumer's safe path. A regeneration on each new major version is a release-checklist item.
- **`CollationId` is undocumented** (F3). The on-disk lookup depends on it, and only for the backup
  reader. Its equality with the on-disk id is to verify (D9).
- **The wire key is derived, not read.** `CodePageForWireCollation` assumes the wire's LCID, fUTF8
  and SortId equal `COLLATIONPROPERTY`'s (D9). Spec 092's page check fails a catalog statement by
  name where they disagree, so a wrong assumption is loud, not silent.
- **Answers may depend on the collation, not only the page.** F17 checked one second collation per
  page, of another kind or version; the other collations of a page are not probed.
- **x86-64 is slower than the numbers here** (Follow-ups 1). The benchmarks ran on arm64 only.
- **The generator's own SQL** is guarded by its assertions and row counts (D2), not trusted. F11 is
  why it reads bytes in a database of the page, never through `COLLATE`.
