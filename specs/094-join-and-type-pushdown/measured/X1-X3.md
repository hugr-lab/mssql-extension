# Spec 094 experiments (SQL Server 2025, 17.0.5035.5, throwaway container, 2026-11-24)

Scripts: `scripts/` (setup.sql, x1_vector.sql, x2_forms.sql, x2_rest.sql; probe.sh runs them).

## X1: VECTOR_DISTANCE against DuckDB's functions

`dbo.vec`: 2000 `vector(3)`, every component a multiple of 1/64 (exact in float32), a zero vector, a NULL.
Query vector `[0.5, -0.25, 1.0]`. Values read with style 3 (17 digits) and recomputed in DuckDB on the
same FLOAT[3].

- The result's type: `float` (64-bit), its value a float32 widened (`1.1456439495086670e+000`).
- `'euclidean'` = `array_distance`: 2000 / 2000 bit-equal.
- `'dot'` = `array_negative_inner_product` (the negative dot product): 2000 / 2000 bit-equal; not
  `array_inner_product` (3 equal: the zeros).
- `'cosine'` vs `array_cosine_distance`: 1665 / 2000 bit-equal, the rest within 2.4e-7 (1-2 float32
  ulps; another order of operations). The order of the 2000 rows by distance: 0 disagreements, one tie
  on each side.
- The zero vector: cosine 1.0 on the server, NaN in DuckDB (which orders NaN last). euclidean equal.
- NULL: NULL both; the server orders it first, DuckDB last (NULLS LAST default).
- A dimension mismatch: error 42204 ("The vector dimensions 3 and 2 do not match"); in DuckDB a
  FLOAT[3] / FLOAT[2] pair does not bind.
- `TOP (k) … ORDER BY VECTOR_DISTANCE(…)` and an `sp_executesql` parameter declared `vector(3)`: work.
- 2025 has `VECTOR_NORM(v, 'norm2')`: a zero vector's key can be told apart on the server.

## X2: spatial predicates, the index, invalid geometries

`dbo.geo`: 100000 points on 0..1000, a line, a polygon, POINT EMPTY, NULL, an invalid polygon (a bow tie,
id 200005), a line, a CIRCULARSTRING; `six_geo` GEOMETRY_AUTO_GRID, BOUNDING_BOX (0, 0, 1000, 1000).
@box = (100..300)², @far = (5..20)² (overlaps the invalid polygon). Index use from STATISTICS XML (the
plan names `six_geo`; sqlcmd needs `-y 0`, else the XML is cut at 256 characters).

| form | rows | spatial index | an invalid geometry that is a candidate |
|---|---|---|---|
| `g.STIntersects(@b) = 1` | 4007 | yes | error 6522 / 24144 |
| `@b.STIntersects(g) = 1` | 4007 | yes | error |
| `g.STWithin(@b) = 1` | 4004 | yes | error |
| `g.STDistance(@b) <= 10` | 4837 | yes | error |
| `g.Filter(@b) = 1` | 4127 (a superset) | yes | error when evaluated exactly (no index: a PK seek) |
| `g.STIntersects(@b1.STUnion(@b2)) = 1` | 4026 | yes | error |
| `g.STIntersects(@b1) = 1 OR g.STIntersects(@b2) = 1` | -- | no | error (every row evaluated) |
| `g.STEnvelope().STIntersects(@b) = 1` (DuckDB's `&&`) | -- | no | error (every row evaluated) |
| `CASE WHEN g.STIsValid() = 1 THEN … END = 1` | 4007 | no | no error |
| `g.Filter(@b) = 1 AND CASE WHEN g.STIsValid() = 1 THEN … ELSE 1 END = 1` | 4007 | yes | error if Filter is evaluated exactly |

- An invalid geometry fails any exact method (`STIntersects`, `Filter` evaluated exactly, `STEnvelope`,
  `STDistance`, `STArea`) the moment a row is a candidate: error 6522 wrapping 24144, the batch ended.
  `STIsValid()` itself does not fail. With the index, a row the primary filter drops is never
  evaluated -- so a pushed predicate fails or not by where the invalid rows lie. A pushed form must not
  depend on that: guard it (`CASE WHEN g.STIsValid() = 1 …`), which loses the index, or force the index
  and use the index-only `Filter` (to measure: whether `WITH (INDEX(six))` keeps Filter from evaluating).
- `Filter` is a superset of `STIntersects`, not of `&&`: the index holds a geometry's cells, not its
  envelope, so a geometry whose envelope meets the box but which does not can be dropped. `&&` has no
  index form.
- DuckDB's `&&` (core, no spatial extension) against the server's `g.STEnvelope().STIntersects(@box)`,
  2007 rows: 2004 equal, 0 different; the invalid polygon (DuckDB answers, the server fails) and NULL.
- A CIRCULARSTRING: the server's envelope meets the box; DuckDB reads it NULL under geometry_as
  'geometry' (D6). A pushed predicate keeps the row, DuckDB's own drops it: the server's answer can only
  be a superset that DuckDB re-checks, never consumed.
- POINT EMPTY's `AsBinaryZM()` is a MULTIPOINT EMPTY; empty meets nothing either side.

## X3: geography

A geodesic box (10..20 E, 70..71 N) against points near its edge: the server's STIntersects is geodesic,
DuckDB's `&&` on `GEOMETRY('OGC:CRS84')` planar. (70.9 N, 20 E) is inside the planar box and outside
the geodesic one. A geography predicate is not DuckDB's: not pushed.
