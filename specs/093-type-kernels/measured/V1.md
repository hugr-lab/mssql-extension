# V1 — the `vector` wire form under VECTORSUPPORT

**Question** (spec 093 § Experiments, V1): with LOGIN7 FeatureExt `0x0E` VECTORSUPPORT negotiated,
how does the server send a `vector(3)` and a `vector(3, float16)` column? This settles D4's TYPE_INFO
byte order, the float16 form, and which version to request.

**Method** (2026-11-13, SQL Server 2025 17.0.5035.5, throwaway containers). The raw output is kept
out of the repository; T3 commits the values as the kernel's test vectors.
- **Tables.** `dbo.vt (id int, v vector(3))`, `dbo.vt16 (id int, h vector(3, float16))` and
  `dbo.vbig (id int, v vector(1998))`, with `PREVIEW_FEATURES = ON` for float16. The rows are V2's.
- **Client.** An ad hoc client on the extension's `TdsConnection`. It was linked against a
  probe-only copy of `BuildLogin7` that appends `0E 01000000 <version>` after the UTF8SUPPORT
  feature.
- **Runs.** For VECTORSUPPORT versions 0, 1, 2 and 3, the client logged the FEATUREEXTACK and printed
  the raw response to `SELECT id, v …` as hex.
- **Expressions.** A second run selected `v AS x, CAST(v AS vector(3)), ISNULL(v, v)`, with version 1
  and with no feature.

**Result.**

- **Negotiation.** A request for version 1, 2 or 3 is acknowledged with `0E 01000000 01`, which is
  version 1. A request for version 0 is refused: the server closes the connection during login, and
  no error token is sent.
- **float32 under version 1.** The TYPE_INFO is `F5 <USHORT max length> <BYTE element type>`.
  - For `vector(3)` the COLMETADATA reads `ff000000 0900 f5 1400 00 01 7600`:
    - UserType 255;
    - flags 0x0009: nullable, usUpdateable 2 (unknown);
    - type `0xF5`, max length 20, element type 0;
    - then the name `v`.
  - For `vector(1998)` the max length is 8000 (`f5 401f 00`).
  - A row value is a USHORT length and the bytes as stored on disk (V4):
    `1400 a9 01 0300 00 000000 0000803f 00000040 00004040`.
    - The header is `A9 01`, the dimensions as a u16, the element type as one byte, and three zero
      bytes.
    - The elements follow as float32 LE.
  - The NULL row was sent as an NBCROW bit (`d2`).
- **float16 under version 1.** The server sends JSON text, as in V2: `a7 ffff 0904002600`, which is
  varchar(max), PLP, `Latin1_General_100_BIN2_UTF8`. UserType is 255 here too. No version above 1
  was acknowledged, so the `0xF5` read form of a float16 vector was not seen.
- **UserType 255.** It appears in every form:
  - `0xF5`, and the JSON text with or without the feature;
  - a column, an alias of it, `CAST(… AS vector(3))` and `ISNULL(v, v)`. The `ISNULL` column's flags
    are 0x0021.

  So a raw scan can recognise a vector from its COLMETADATA alone.

**For D4.**
- Request version 2, and accept an acknowledgement of 1.
- With an acknowledgement of 1, each column decides its form from its COLMETADATA: a float32 column
  streams `0xF5`, and a float16 column streams JSON.
- The kernel's header check is the one D1 lists: `A9`, `01`, dims equal to n, element type 0 / 1,
  and zero reserved bytes.
- The TYPE_INFO is the length, then the element type.
