# J1 — whether the 2025 `json` type is comparable on the server

**Question** (spec 093 § Experiments, J1): D2 keeps `json` out of pushed comparisons and keys
"whatever its read form" if the server cannot compare it. Can it?

**Method** (2026-11-15, SQL Server 2025 17.0.5035.5, compatibility level 170, a throwaway container
on the image `images.txt` pins). The raw output is kept out of the repository. One table,
`j (id int NOT NULL, j json NULL)`, with rows `{"a":1}`, `{"a":2}`, `{"a":1}` and NULL; each
statement below was run as its own batch.

**Result.** Nothing but `IS NULL` is accepted.

| statement | answer |
|---|---|
| `WHERE j = N'{"a":1}'` (also `<>`, `<`, `IN (…)`) | Msg 402: "The data types json and nvarchar are incompatible in the equal to operator" (not equal to, less than) |
| `WHERE j = CAST(N'{"a":1}' AS json)` | Msg 13636: "The JSON data type cannot be compared or sorted, except when using the IS NULL operator." |
| `sp_executesql N'… WHERE j = @p'`, `@p nvarchar(4000)` / `varchar(8000)` | Msg 402 (nvarchar / varchar) |
| `WHERE j IS DISTINCT FROM N'…'` | Msg 402 ("is not operator") |
| `WHERE j LIKE N'%a%'` | Msg 8116: argument data type json is invalid for argument 1 of like function |
| `ORDER BY j`, `GROUP BY j`, `JOIN … ON a.j = b.j`, `MERGE … ON t.j = s.j` | Msg 13636 |
| `SELECT DISTINCT j` | Msg 421: "The json data type cannot be selected as DISTINCT because it is not comparable." |
| `CREATE UNIQUE INDEX … (j)` / `PRIMARY KEY (j)` | Msg 1978 / Msg 1919: invalid for use as a key column |
| `WHERE j IS NULL` | the NULL row |

Aside: the server stores a `json` value normalised. `{ "a" : 1 }` was read back as `{"a":1}`.

**For D2.**
- `json` is on the "compared unlike DuckDB" side: `ComparisonDiffersFor("json")` is true. A
  comparison of a `json` column runs in DuckDB over the text it read. An `IS [NOT] NULL` test is
  still pushed. `IS NULL` was measured; `IS NOT NULL` was not, and 13636's wording ("except when
  using the IS NULL operator") is the evidence that it is accepted too.
- A table with no usable key that has a `json` column cannot be keyed by all its columns. On the
  row-by-row path its UPDATE / DELETE are refused by name, as for an `xml` column; a statement the
  server is sent whole (`mssql_dml_pushdown`) needs no key and runs. A staged MERGE whose ON
  compares a `json` column is refused by name too. Before, both went to the server as a join or a
  MERGE ON comparing the `json` column, which the table above shows refused with 13636 (inferred
  from that, not run through the catalog with the old code).
- Before this, a filter on a `json` column was pushed and the query failed. `WHERE doc = '…'`
  through the catalog on this image gave "SQL Server error [402, severity 16]: The data types json
  and nvarchar are incompatible in the equal to operator" (rowversion_and_json_types.test, run with
  `json` back on the comparable side). Nothing was silently wrong: the server refused every such
  statement.
- A `json` column cannot be a rowid key: no index can hold it.
- `OrdersLikeDuckDB` already left `json` out, so an `ORDER BY` was never pushed.
