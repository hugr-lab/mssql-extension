# K1 — `GEOMETRY('OGC:CRS84')` downstream: DuckDB, Parquet, DuckLake

**Question** (spec 093 § Experiments, K1): D6 reads `geography` as `GEOMETRY('OGC:CRS84')` and
`geometry` as `GEOMETRY`. Does the label work downstream with no server: casts, Parquet, DuckLake? Is
anything lost on the way, Z / M or EMPTY?

**Method** (2026-11-20, no server, synthetic values; the raw output is kept out of the repository).
- **DuckDB** at this repository's pin, `v2.0.0-dev70230`, with no spatial extension.
- **DuckLake** through mssql-ducklake's own build, `v2.0.0-dev88614`, with its locally built
  `ducklake` extension: the binary the importer runs. The DuckLake catalog is a local file, its data a
  local directory.
- **WKB** fed to `GEOMETRY` is G1's prototype output: point ZM, MULTIPOINT EMPTY, the curve codes and
  FullGlobe's 126.

## DuckDB, no extension

- **The CRS label works without the extension.**
  - `GEOMETRY('OGC:CRS84')` is a type of its own (`typeof`). It casts to `GEOMETRY` and back.
  - `OGC:CRS83` is built in too.
  - `EPSG:4326`, `EPSG:4269` and `EPSG:3857` are refused at bind: `unrecognized coordinate system …
    Load an extension that can identify this coordinate system`.
  - **For T6:** a source column labelled `EPSG:n` exists only where the spatial extension is loaded.
- **WKB into `GEOMETRY` (a BLOB cast):**
  - ISO Z / M / ZM are taken: `POINT ZM (1 2 3 4)`;
  - MULTIPOINT EMPTY is taken;
  - the curve codes 8 – 10 and FullGlobe's 126 are refused (`Unsupported geometry type in WKB`); so
    is a WKT `CIRCULARSTRING`.
- **POINT EMPTY** is DuckDB's own value. Its WKB is a point of two NaN, `0x7FF8000000000000`
  (`\x01\x01\x00\x00\x00` + NaN NaN), not the server's MULTIPOINT EMPTY (G1).

## Parquet (COPY TO, the default GeoParquet 1.0 metadata)

- `GEOMETRY('OGC:CRS84')` is written and read back as `GEOMETRY('OGC:CRS84')`. The `geo` key holds
  the column, its `geometry_types` (`Point Z` for a Z value) and its bbox.
- **A `GEOMETRY` with no CRS is read back as `GEOMETRY('OGC:CRS84')`.** GeoParquet 1.0's default CRS
  is CRS84 when none is given. A planar `geometry` (SRID 0, 3857) written to Parquet and read back
  gains a geographic label it never had.
- **A `GEOMETRY` holding an M value is written as `BLOB`.** No `geo` entry is written for it, and it
  is read back as BLOB: GeoParquet 1.0 has no M. A Z value keeps the type.
- `GEOPARQUET_VERSION 'V2'` writes Parquet's own GEOMETRY logical type
  (`GeometryType(crs=<null>)`). Such a column, ZM included, reads back as `GEOMETRY`.

## DuckLake

A table `(id INT, geog GEOMETRY('OGC:CRS84'), geom GEOMETRY)` was created. Into it went:
- POINT, POINT Z and POLYGON in `geog`;
- POINT, POINT ZM, LINESTRING M and POINT EMPTY in `geom`;
- a NULL.

It was read back, detached, attached again and read back again.

- **Every value is kept**, Z, M, ZM and POINT EMPTY included, in the same session and after the
  re-attach.
- **The CRS is not kept.** The column created as `GEOMETRY('OGC:CRS84')` describes as `GEOMETRY`
  straight after the CREATE and after the re-attach. The data file's column is Parquet's GEOMETRY
  logical type with `crs=<null>`, for both columns.
- **No inlining.** DuckLake warns that it writes the rows to files instead of inlining them, "because
  column … has type GEOMETRY, which cannot be inlined".

## What it means

- **For T5 (D6), the reader's types hold as designed.** `GEOMETRY('OGC:CRS84')` needs no extension,
  and every value the kernel gives (types 1 – 7, Z / M / ZM, EMPTY) is a `GEOMETRY`. Curves and
  FullGlobe must stay refused or BLOB (D6).
- **For the import, DuckLake drops the label.** A lake does not tell a `geography` column from a
  `geometry` one by its type. The CRS, or the SQL Server type, has to travel some other way:
  - the importer's own metadata;
  - a column comment;
  - or a DuckLake change, which is not this repository's to make.

  That is mssql-ducklake's call (its specs 022 – 024). This spec records it in § Risks.
- **For a COPY TO Parquet of a `geometry` column, the defaults change the data's meaning.** Under
  GeoParquet 1.0 a planar column reads back as CRS84, and one with M as BLOB. `GEOPARQUET_VERSION
  'V2'` keeps both. This is documented for users, not changed: it is DuckDB's writer.
