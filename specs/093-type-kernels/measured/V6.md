# V6 — INSERT BULK into a vector column

**Question** (spec 093 § Experiments, V6): which bulk forms does the server take for a vector
column, with and without VECTORSUPPORT? This decides D4's COPY / INSERT BULK / `#stage` path:
`0xF5`, the stored bytes as `varbinary`, or JSON text.

**Method** (2026-11-13, SQL Server 2025 17.0.5035.5, throwaway containers). The raw output is kept
out of the repository.
- **Tables.** `dbo.vt (id int, v vector(3))` and `dbo.vt16 (id int, h vector(3, float16))`, with
  `PREVIEW_FEATURES = ON`.
- **Client.** An ad hoc client on the extension's `TdsConnection`.
  - "v1" below means V1's login: version 1 was requested and acknowledged.
  - "none" means the stock login, with no feature requested.
- **Each case, on its own connection.** The client sent `INSERT BULK <table> ([id] int, [v]
  <declared>)`. Then it sent one BULK_LOAD: a COLMETADATA giving `v` the TYPE_INFO below, one ROW,
  and DONE.
- **Checks.** Each answer was read for an ERROR token, and the stored rows were read back as text.
- **Values.**
  - In most cases the value is `[4, 5, 6]`, as its bytes (`a9 01 0300 <et> 000000 …`) or as JSON
    text.
  - Cases 12 and 18 send `[4, 5]` as bytes: 16 bytes for a 20-byte column.
  - Case 10 sends `"[4,5]"` as JSON.
  - Case 19 sends a float32 value whose header says float16.

**Result.**

- **Declared `vector(n)`.** The COLMETADATA may be `0xA5` (varbinary) on any session, or `0xF5` only
  on a session that acknowledged the feature (4816 otherwise).
  - With `0xA5`, the server takes the bytes as sent, for float32 and float16 alike, with the feature
    and without it. The stored values read back as sent.
  - A string type is refused under a declared `vector(n)` (4816).
  - A wrong length is 7347, and a header that does not match the column is 42206.
- **Declared string type** (`nvarchar(4000)`, `varchar(8000)`, `nvarchar(max)`). The server converts
  JSON text. A declared `varbinary(n)` is refused at INSERT BULK (206).
- **The PLP length.** A JSON PLP with a known total length fails the conversion (13609). The same
  value with the unknown length is taken. The cause was not investigated. The extension's PLP
  encoder always writes the unknown length (`codec/string_codec.cpp`), so it is not affected.

**For D4.**
- **One bulk form.** COPY / INSERT BULK / `#stage` declare `vector(n)` / `vector(n, float16)`. They
  send `varbinary(length)` with each value's header and elements, on every session (derived). One
  encoder covers both negotiations and both element types, and the server stores the bytes as sent.
- **No JSON in bulk.** JSON is not needed on the bulk path. It would be exact only from 9
  significant digits, which is derived from V2, not measured here.
- **The statement path** keeps `CAST(N'[…]' AS vector(n))` with `%.9g`.
