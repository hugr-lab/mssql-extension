# G6 — the bare spatial read against the server's WKB

**Question** (spec 093 § Experiments, G6): what does T5's read gain over the server-side conversion?
The read sends the stored MS-SSCLRT bytes and the client decodes them; the conversion is today's
catalog read through `STAsBinary()`, or `AsBinaryZM()`. Measured for the PR body.

**Method** (2026-11-20, the shared test server: SQL Server 2022 under Rosetta on an Apple M-series
host, the client on the same host; T5's release build).
- **Data.** `dbo.g6_points (id int PRIMARY KEY, g geometry)`: 1,000,000 points, created for the
  measurement and dropped after it. Each point is 22 bytes stored, 21 as WKB.
- **Variants.** Three, interleaved, three rounds each, with `MSSQL_COUNTERS=1`:
  - **A:** `SELECT sum(octet_length(g::BLOB)) FROM db.dbo.g6_points`, the catalog read (T5: bare,
    decoded to `GEOMETRY`);
  - **B:** the same over `mssql_scan(…, 'SELECT g.AsBinaryZM() AS g …')`;
  - **C:** the same over `mssql_scan(…, 'SELECT g.STAsBinary() AS g …')`.
- **Server CPU.** `sys.dm_exec_query_stats` for each statement (three executions each).

**Result.**

| variant | wall (3 runs) | server CPU / run | wire in | client kernel |
|---|---|---|---|---|
| A bare + client kernel | 0.304, 0.299, 0.305 s | 299 ms | 38,002,760 B | spatial, 163 ns / value |
| B `AsBinaryZM()` | 0.959, 0.941, 0.949 s | 946 ms | 37,003,128 B | binary, 3 ns / value |
| C `STAsBinary()` | 0.940, 0.937, 0.936 s | 933 ms | 37,003,128 B | binary, 5 ns / value |

- **Faster.** The bare read is 3.1× faster in wall time, and the server spends 3.1× less CPU. The
  conversion's cost was the server's: B's and C's stream wait (`read`) is 0.82–0.88 s of their 0.93–0.95
  s, against 0.06 s for A.
- **The wire carries 2.7 % more:** 22 bytes a point stored against 21 as WKB.
- **The client kernel costs 163 ns a point**: 0.16 s of A's 0.30 s, well above the binary kernel's copy.

**After the vectorized kernel** (the same day, the same three variants interleaved). One decoder per
column-chunk keeps its arrays from value to value; a single point or line takes a path of its own; the
WKB is sized first and written straight into the vector's string heap.

| variant | wall (3 runs) | server CPU / run | client kernel |
|---|---|---|---|
| A bare + client kernel | 0.304, 0.305, 0.307 s | 302 ms | spatial, **10.2 – 10.5 ns / value** |
| B `AsBinaryZM()` | 0.945, 0.935, 0.937 s | 935 ms | binary |
| C `STAsBinary()` | 0.934, 0.945, 0.932 s | 933 ms | binary |

- **The kernel is 16× faster:** 163 to 10 ns a point, 10 ms for the million.
- **The wall time is the server's now.** A's stream wait (`read`) is 0.22 s of its 0.30 s, where it was
  0.06 s with the kernel holding the pipe. The read stays 3.1× faster than either conversion and costs
  the server 3.1× less CPU.

**Beyond points** (the same day, the vectorized kernel, then with each figure's points copied as one run:
x / y as stored, a geography's swapped, only Z / M checked for NaN). 50,000 values of each shape, each
read twice; `MSSQL_COUNTERS`' kernel ns per value:

| shape | points | before the run copy | after |
|---|---|---|---|
| LINESTRING | 10 | 53 | 40 |
| POLYGON | 5 | 40 | 37 – 40 |
| POLYGON with a hole | 10 | 52 | 45 |
| MULTIPOLYGON of two | 8 | 73 – 76 | 70 |
| GEOMETRYCOLLECTION (point, line, polygon) | 6 | 91 | 87 – 91 |
| POINT (1M, above) | 1 | 10 | 12.5 |

- **The points no longer dominate.** What is left is about 35 ns a value: reading and checking the
  figures and shapes, the pass that sizes the WKB before the one that writes it, and the string's
  allocation in the vector's heap.
- **The read is the server's.** The kernel is 10 – 15 % of the read; the stream waits on the socket for
  the rest.
- **Left to try:** a path of its own for a value of one figure (a line, a polygon without holes), past
  the shape tree.
